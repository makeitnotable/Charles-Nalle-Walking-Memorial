## 1. The problem

On iPhone (iOS 26 Safari; the client uses the address-bar-on-top layout), the areas behind the address bar and the bottom toolbar are painted as **solid dark bands** on every page. The goal is for those bars to behave like Liquid Glass: the page shows through them, so the site reads full bleed.

The client's screenshots were measured pixel by pixel:

| Screenshot | Bar colour | Matches |
|---|---|---|
| `/paintings` (corridor intro) | `#100a06` exactly | `--color-neutral-2`, the page-transition curtain |
| `/bakery` (chapter hero) | `#100a06` exactly | same |
| `/map` (walk mode) | `#1d1411` exactly | `--color-primary-2`, the page ground |

## 2. How Safari 26 decides the bar colour

Apple doesn't document this. The rules below come from community reverse-engineering, and they match what this site does.

- **`theme-color` is ignored** on iOS 26. The bars are tinted from CSS instead.
- **What Safari reads.** It looks at `position: fixed` / `position: sticky` elements near the viewport edges. From each one it reads `background-color` and `backdrop-filter`, **on the element itself**.
- **Which elements count.** An element must be:
  - within about **4px of the top** or **3px of the bottom**;
  - at least **80% of the viewport wide**;
  - at least **3px tall**.
- **Hiding tricks don't work.** Elements at `opacity: 0`, `visibility: hidden` or `pointer-events: none` are **still read**. Only **`display: none`** removes an element reliably.
- **What Safari skips.** **Pseudo-elements** (`::before`/`::after`) and **absolutely positioned children** of a fixed element are not read.
- **Fallback.** With no qualifying element, Safari uses the `body` / `html` background. A transparent root falls back to white, so never make `html` or `body` transparent.
- **What the reading does:**
  - an **opaque** colour becomes a solid band behind the bar;
  - a **semi-transparent** one lets the page show through (reported by jahir.dev, where a semi-transparent fixed overlay at the bottom made the toolbar transparent).
- **At `scrollY = 0`** the top bar tends to show the fallback root colour, because nothing sits above the top of the document. Real page pixels show behind it once the page is scrolled.

Sources:
- https://1ar.io/updates/safari-26-liquid-glass-web/
- https://github.com/andesco/safari-color-tinting and its demo, https://safari-color-tinting.pages.dev/
- https://jahir.dev/blog/safari-toolbar
- https://benfrain.com/ios26-safari-theme-color-tab-tinting-with-fixed-position-elements/
- WebKit bug 302272 (closed as by design)

## 3. What is causing the bands on this site

The site was audited in a 390×844 mobile Chromium context. On every route, at 10 scroll depths, the audit listed every fixed or sticky element that meets Safari's size and position rules.

| Element | Where | Why it matters | Fix |
|---|---|---|---|
| `#curtain-panel` (`.curtain-panel`) | every page (`Base.astro`) | Fixed, `inset: 0`, **opaque `#100a06`**, always rendered and only parked off-screen with a transform. | `#curtain-text` (`.curtain-text`) | every page | Fixed, `inset: 0`, `opacity: 0` but rendered, so it competes at both edges | `display: none` except while animating |
| Corridor stage (`Museum.tsx`, `sticky top-0 h-dvh … bg-primary-2`) | `/paintings` | Sticky, full-screen, **opaque `#1d1411`**, so the bars go solid while walking the hall | Opaque ground moves to `::before`; the element itself carries the glass value |
| `.walk-rail` | 5 chapter pages | Fixed, full-width, 3px, transparent | **Left untouched** (see §7) |
| Map card strip (`TroyMap.tsx`, `fixed right-0 bottom-0 left-0`) | `/map` | Fixed, full-width, transparent | **Left untouched** (see §7) |
| Nothing at an edge | `/`, `/about`, `/people`, `/404`, chapter bottom edges | Safari falls back to the page ground, which is a solid band | Two invisible 4px glass strips, one per edge, on every page |

Things that are **not** the fix, and should not be "improved":

- **The theme-color sampler.** The inline script in `Base.astro` and the `data-edge-*` attributes feed `<meta name="theme-color">`, which iOS 26 ignores. Leave them alone: Chrome on Android still uses them.
- **The old `.chrome-tint` strips (v12, removed in v14.3).** They were 2px tall, below Safari's 3px minimum, and painted opaque, so they showed up as visible lines. Don't bring them back.
- **Changing `svh`/`dvh`/`lvh` or the page layout.** Not needed, and forbidden by §0 (`AGENTS.md` records why `lvh` failed in rounds 1–2).

## 4. The design of the fix: why no pixel can change

There is one token, `--edge-glass: rgb(29 20 17 / 0.02)` (the page brown at 2%). It is the value Safari reads from anything pinned to an edge. By construction it is **never visibly painted**:

1. **Corridor stage and curtain panel.** The `--edge-glass` fill sits on the element itself. An opaque `::before` of the *original* colour covers it exactly (same box, painted above the element's own background and below every child). What you see is identical; what Safari reads is glass.
2. **Edge strips.** These are drawn at `opacity: 0`, so they paint nothing. Safari still reads their background. They are also:
   - `pointer-events: none`;
   - iOS/iPadOS only, via `@supports (-webkit-touch-callout: none)`;
   - out of the `Base.astro` sampler's reach (it reads 4px in from each edge and skips non-opaque colours).
3. **Curtain panel and label, `display: none` at rest.** At rest they were already invisible (parked off-screen / `opacity: 0`). They become `display: block` / `flex` in exactly the states where they were visible before:
   - `.curtain-covered` (page arriving mid-transition);
   - `.is-active` (added by `curtain.ts` for the whole animation, removed when it parks).
4. **Chrome on Android.** It used to read `#100a06` from the curtain during transitions. The panel now declares `data-edge-top/bottom="#100a06"`, so the existing sampler keeps doing exactly that.

Because nothing visible uses `--edge-glass`, **its alpha can be tuned on a device without any visual risk** (see §8).

## 7. If the phone still shows solid bands

Work down this list and stop at the first step that works. Anything that would change a pixel needs the owner's written sign-off **before** implementation.

1. **Raise the glass alpha.** Change only `--edge-glass`, for example to `rgb(29 20 17 / 0.3)`, then `0.6`. No visual risk, since the token is never visibly painted. Re-run `qa:snap` anyway.
2. **Chapter pages, top bar only.** The `.walk-rail` is a qualifying fixed element with a transparent background and may be outranking the top glass strip. Giving the rail `background-color: var(--edge-glass)` would tint its 2px gaps by about 2%. That is **a visible pixel change**, so it needs sign-off, and `allowedRoutes` must then list the 5 chapter routes.
3. **`/map`, bottom bar only.** The same situation applies to the card strip, with the same sign-off requirement.
