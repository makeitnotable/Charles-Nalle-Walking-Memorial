### Why each one failed

**Item 2 — the chapter strip was shipped to a different spec than §5.1's.**
The wiring is correct and was never the problem: `[chapter].astro` passes
`topBar="section"`, and `Base.astro` writes `sectionGroundAt(4)` onto
`.edge-glass-top` as an opaque colour. The strip itself was wrong on two
counts:

| | §5.1 specified | Phase B shipped |
|---|---|---|
| Height | **12px** | **4px** |
| Gate | ungated, "so Mac Safari gets them too" | still inside `@supports (-webkit-touch-callout: none)` |

§3's evidence table puts the qualifying minimum at **3px on iOS and 6px on
macOS**, and records **12px** as the height bleedblend measured as reliably
working. 4px is one pixel over the iOS floor and *under* the macOS floor. The
gate is not what blocked iOS — A2 measured it firing `true` on Wil's phone —
but it excluded Mac Safari completely. §5.1 also shipped knowingly unverified:
*"the strip is `opacity: 0` and invisible, so if the mechanism does not take it
costs nothing."* It did not take.

**Item 3 — the same wall that killed §5.2.3, showing up at rest.**
`Museum.tsx:2288` makes the stage `sticky top-0 h-dvh overflow-hidden`, and the
canvas is `position: absolute; inset: 0` inside it. The scene background, the
fog and the stage's `::before` ground are all `#1d1411` — exactly the flat
value measured, cut exactly at the visual viewport's edge. **Pinned content is
clipped at the visual viewport**, which is what A2 measured when it dropped
§5.2.3. `/map` works because `.map-shell` is an ordinary in-flow block; the
corridor is pinned, so it stops at the bar. Same cause, different symptom.

**Item 1 — see-through at the page top is not available on iOS 26.**
At rest the visual viewport is screen 107–752, there is no document offset
below 0, and out-of-flow boxes are clipped to the visual viewport. So *nothing
the page draws can appear behind the address bar at rest* — not content, not a
fixed box. The only reachable mechanism is the **tint**: the same edge strip,
fed a colour. That produces a **matched-colour band, not see-through.**

## §5.5 `/map`: a matched-colour band behind the address bar (approved, pending)

**What it is not:** see-through. See §"Why each one failed" above — impossible
at rest on iOS 26.

**Mechanism.** The existing `.edge-glass-top` strip, on `/map` only, carrying
the map's own colour at the top edge, so the band matches instead of
contrasting. **Blocked by the same finding as §5.1:** test 4 showed the strip is
not read at `opacity: 0`, so this needs test 5's answer before it can be built.
Note the band would sit over a textured map, so unlike a flat section ground it
cannot hide by matching — the lower the usable opacity, the better this looks.

**Wil's condition: no hardcoded grey — sample it live**, so it tracks pan and
zoom. Mapbox's WebGL context is created without `preserveDrawingBuffer`, so a
`readPixels` after the frame returns empty. The way that works is a 1×1
`readPixels` at the top edge taken **synchronously inside Mapbox's own `render`
event**, before the buffer is cleared, throttled onto `Base.astro`'s existing
100ms sampler schedule. That avoids the `preserveDrawingBuffer` penalty
entirely. Cost to be measured and reported before it ships. If it proves
impractical, report the alternatives and their costs to Wil rather than
building one.

**`/map`'s bottom bar is out of scope** — already correct, measured above.

- **The bars are ALREADY GLASS.** With no edge element at all, page content
  showed behind the expanded bottom toolbar and behind both bars once
  minimized. Round 7's `--edge-glass` strips are inert. The top bar at rest
  reads the page brown only because nothing exists above document offset 0 —
  the root-background fallback, not a tint.
- **In-flow vs pinned is the asymmetry that decides everything.** In-flow
  content renders behind the bars (the ruler reached document offset ~737 with
  a 645 viewport). A PINNED box's overflow does not: it is clipped at the
  **visual viewport**. Measured: of **160px** of requested bleed, **21px**
  rendered, stopping exactly at the viewport's top edge. That is why the map
  fix works (the shell grows in flow) and the corridor bleed cannot.
- **`cameraForBounds` ignores its `padding` option** in this Mapbox version:
  `bottom: 240` and `bottom: 240 + E` return identical zooms, and removing the
  `+ E` changed no pixel. What it respects is the map's own padding
  (`setPadding`) and the transform height. Worth knowing before touching the
  map's camera again.
- **The `@supports (-webkit-touch-callout: none)` gate fires on Wil's phone**
  even with Request Desktop Website on (`navigator.platform` reads `MacIntel`).
  **Gate on CSS, never on the user-agent, and never on `pointer`/`hover`** —
  desktop mode can change those.

### MEASURED on Wil's iPhone — Phase A, 2026-09-17 (this supersedes the guesswork below)

The lab (`/glass-lab`, shipped as `578a5ac`) was run in the **Top** layout on an
iPhone at 390×844 CSS px, dpr 3. What it found overturns this round's premise:

**The bars are already glass. Nothing needs to be made translucent.**

- **Test 1, with NO edge element at all** — both strips `display: none`, the rail
  off, the stage declaring no background — showed page content behind the
  **expanded bottom toolbar**, and behind **both** bars once they minimize.
  bleedblend's claim is the correct one; Jahir's semi-transparent-overlay
  finding does not apply here.
- **Round 7's `--edge-glass` strips are inert.** Test 3 (fully clear) is
  indistinguishable from test 1 (no strips at all), and test 5 showed content
  through the bottom bar with *every* stage background, including an opaque
  `#1d1411`. The strips neither help nor hurt. They are a retirement
  candidate, not a mechanism. **The one exception is the chapter pages' top
  strip** (§5.1): that IS the mechanism that tints the address bar at rest, so
  it stays.
- **The top bar at rest is not a tint.** It reads the page brown because
  nothing exists above document offset 0 — the root-background fallback. Scroll
  one pixel and content appears behind it.

**The covered regions, at rest (Top layout):**

| | CSS px |
|---|---|
| Top bar (status bar + address bar) | **107** |
| Layout viewport (`clientHeight`, always `svh`) | **645** |
| Bottom toolbar | **92** |
| Screen (`lvh`) | **844** |
| `lvh − svh` (the pair, as CSS reports it) | **198.98** |

Derived two independent ways that agree: from the at-rest screenshot, ruler
offset `0` sits at screen y ≈ 107 and content still renders to offset ≈ 737 at
the screen's bottom edge; and arithmetically, 107 + 645 + 92 = 844 with
107 + 92 = 199 = `lvh − svh`. **Minimized, nothing is covered** — content runs
from offset 0 at the very top to ~840 at the very bottom, with the status bar
and address pill floating over it.

`dvh` is 645 at rest and 752.66 minimized; `env(safe-area-inset-bottom)` is 0 at
rest and 34 minimized. **This is why E, X and Y must be static** (the v14.3
jitter note): anything sized in `dvh` changes height as the bars move. Prefer
the self-zeroing form `min(110px, calc(100lvh - 100svh))`, which is 110 where
there are bars and **0** where `lvh == svh`, so desktop and Android need no
feature gate at all.

**Gate on CSS, never on the user-agent.** Every metrics block came back with a
**macOS** user-agent —
`Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) … Version/26.6.1 Safari/605.1.15`
— while the screen, the safe-area insets and the bar behaviour were
unmistakably an iPhone ("Request Desktop Website", most likely). UA spoofing
does not change CSS feature support. Phase A2 probes the real
`@supports (-webkit-touch-callout: none)` rule that round 7 already relies on,
prints both gate values on the page and carries them at the top level of the
copied results, so the numbers come from the device rather than from inference.

### Known (multiple sources agree)

- **`theme-color` is ignored.** The bars are tinted from the `<body>` background (then `<html>`), and from `position: fixed/sticky` elements near the edges. The WebKit observer updates the tint live as colours change.
- **Qualifying elements.** An element counts when it is:
  - within about 4px of the top, or about 3px of the bottom on iOS (partially off-screen still counts: `bottom: -8px` with `min-height: 12px` was sampled);
  - at least 80% wide on iOS, and at least 90% wide on macOS;
  - at least 3px tall (6px or more on the Mac, per bleedblend).
- ~~**Still read:** `opacity: 0`, `visibility: hidden` and `pointer-events: none`
  elements.~~ **DISPROVEN ON THE DEVICE, 2026-09-17 (phase C, test 4).** An
  `opacity: 0` element is **NOT** read on iOS 26.6.1 — see "Test 4's result"
  below. `pointer-events: none` is still fine (every configuration that worked
  had it). This single line is what §5.1 was designed on, and it was wrong.
- **Not read:** `display: none`.
- **Also not read (reported):** `::before`/`::after` on fixed elements, `position: absolute` children of fixed elements, and elements with `backdrop-filter`.
- **Ordinary sections at the edge are sampled too**, not just fixed ones (bleedblend).
- **A 12px strip** at the edge with the wanted colour is a working way to force a tint (bleedblend).
- **iOS Chrome-style `transparent` quirk.** WebKit treats the `transparent` keyword as black at alpha 0, which can band during transitions. Write `rgba(r,g,b,0)` instead.
- **Fixed full-viewport images stop at the bars.** On iOS 26 they "do not fill the screen": two background-coloured spaces remain top and bottom, while content that scrolls is visible behind the bars (Apple developer forum 809407). This matches the corridor report exactly.
